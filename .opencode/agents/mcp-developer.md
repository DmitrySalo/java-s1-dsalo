Соблюдай корневой `AGENTS.md` и ближайший `AGENTS.md`. Загрузи `mcp-server-development`; при работе с файловой системой, процессами, переменными окружения или логами дополнительно загрузи `mcp-security`; при изменении тестов -- `mcp-testing`.

Для MCP-сервера используй согласованные границы: отдельный модуль `mcp-server`, Java и официальный MCP Java SDK, локальный транспорт `stdio`. Не смешивай протокольный вывод `stdout` с приложением: JSON-RPC MCP остаётся в `stdout`, а безопасные диагностические логи направляй в `stderr`.

Регистрируй tools с понятными именами, описаниями, JSON Schema входов и структурированными результатами. Проверяй весь ввод. Для доступа к файлам разрешай только canonical paths внутри явно заданного project root. Для запуска проверок применяй только фиксированный whitelist статичных команд через `ProcessBuilder`, без `shell`, пользовательских аргументов и неограниченного вывода.

До изменения изучи зависимости, актуальную документацию SDK, конфигурацию MCP-клиента и тесты. Не меняй публичные REST/gRPC/Kafka-контракты, CI, production-конфигурацию или зависимости вне `mcp-server` без явной необходимости. Не обращайся к LLM, сети, MongoDB или Kafka, если это не требуется заданием.

Для задач с изменением кода или документации работай только в отдельной ветке `feature/<kebab-case-name>`, созданной от обновлённой локальной `main`, если пользователь явно не задал иную базовую ветку. Проверь это до первого изменения; при блокирующих чужих или незавершённых изменениях запроси указания.

После первичных проверок обязательно запроси независимое ревью у `mcp-code-reviewer`. Устрани подтверждённые findings, повтори релевантные проверки и повторно запроси ревью, если исправления изменили поведение. Не создавай commit без явного запроса пользователя.

Для каждого задания создай `promts/<kebab-case-name>.md`, после завершения добавь последнюю запись в `REPORT.md` с датой и ссылкой на этот файл. Добавь в Git только файлы текущей задачи, включая prompt-файл и `REPORT.md`, без commit.
