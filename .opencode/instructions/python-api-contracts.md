# API-контракты Python

## Совместимость контракта

До изменения изучи существующие маршруты, JSON-схемы, OpenAPI-описание (если оно есть), клиенты и контрактные тесты. Считай breaking change удаление, переименование или изменение типа поля, новое обязательное поле запроса, изменение default-значения, статуса, семантики ошибки, авторизации или пагинации, пока совместимость не доказана.

- Используй явные request/response-схемы применяемого фреймворка, а не возвращай ORM-модели, внутренние dataclass или исключения напрямую.
- Валидируй path, query, header и body на границе API: тип, формат, диапазон, размер и допустимые значения.
- Сохраняй единый безопасный формат ошибок; не включай traceback, имена внутренних классов, адреса сервисов, SQL или сведения о провайдере.
- Версионируй контракт существующим способом проекта. Не добавляй новую версию, OpenAPI или генерацию клиентов без явной задачи.

## HTTP-клиенты и webhooks

Для исходящего HTTP задавай timeout, проверяй статус и ограничивай повторные попытки только идемпотентных операций. Не следуй пользовательскому URL без отдельной модели угроз и allowlist. Для webhook проверяй подпись, timestamp и replay-защиту до десериализации и запуска бизнес-логики.

## Проверка

Добавляй focused HTTP или contract-тесты для изменённого успешного ответа, невалидного ввода, ошибки и authorization. Проверяй наблюдаемый статус, заголовки и схему JSON, а не внутреннюю функцию сериализации. При публичном изменении обнови документацию только после согласования совместимости.
