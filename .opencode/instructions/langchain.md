# LangChain-агенты

## Границы агента

До изменения изучи существующие prompts, messages, tools, schemas, chains, retrievers и тесты. Агент оркестрирует сценарий, а не заменяет проверяемую бизнес-логику. Сохраняй детерминированные части сценария вне LLM и не меняй поставщика модели, модель, memory или retrieval-стратегию без явной задачи и оценки совместимости.

- Описывай tools узкими типизированными входными и выходными схемами; валидируй аргументы до побочного эффекта и ответ tool после него.
- Отделяй read-only tools от действий, меняющих состояние. Для необратимого или внешнего действия нужен явный контроль вызывающего кода, а не только текстовая инструкция в prompt.
- Ограничивай время, число попыток, объём контекста и максимальное число tool-вызовов. Не добавляй бесконечные циклы и неконтролируемые retries.
- Не подставляй недоверенный ввод в системные инструкции без маркировки и не позволяй модели переопределять policy, доступ к секретам или разрешения tools.

## Данные и наблюдаемость

Не передавай в prompt, traces или логи API keys, токены, персональные данные и полные документы, если для сценария достаточно минимизированного контекста. Явно определяй жизненный цикл memory: область видимости, срок хранения и источник данных. Не включай persistent memory по умолчанию.

Логируй идентификатор запуска, выбранный tool, безопасный итог и ошибку без чувствительного содержимого. Ошибки модели, parser-а и tool-а должны быть различимы для вызывающего кода и не скрываться fallback-ответом.

## Проверка

Покрывай unit-тестами construction prompt/messages, schema validation, routing и обработку ошибок. Интеграционные тесты используют fake/stub LLM и fake tools; не требуют сети, реальных ключей, production vector store или недетерминированных ответов. Для изменения tool с побочным эффектом добавляй тест, доказывающий, что действие не запускается при невалидном или недоверенном вводе.
