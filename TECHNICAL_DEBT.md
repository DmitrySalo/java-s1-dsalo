# Технический долг

Документ декомпозирует ограничения из раздела «Текущие ограничения и технический долг» в [ARCHITECTURE.md](ARCHITECTURE.md). Задачи упорядочены по риску для корректности данных, безопасности и эксплуатации.

## TD-1. Согласовать сетевые порты и health check контейнера

**Приоритет:** высокий.

**Проблема:** `docker-compose.yaml` и `my-scents/Dockerfile` ожидают HTTP-порт `8080` и management-порт `8081`, тогда как `application.yml` настраивает `8087` и `8086`. Health check обращается к несуществующему пути `/manage/health`. Контейнер приложения может быть объявлен нездоровым, а опубликованные порты не соответствуют работающему приложению.

**Задачи:**

1. Сверить порты приложения, Dockerfile, Compose, документации и примеров запуска; выбрать единый набор значений для HTTP и management-портов.
2. Обновить `EXPOSE`, публикацию портов Compose и переменные окружения так, чтобы они соответствовали конфигурации Spring Boot для контейнерного запуска.
3. Настроить health check на фактически доступный endpoint Actuator с учётом `management.server.port` и `management.endpoints.web.base-path`.
4. Проверить, что health check не требует аутентификации в локальном Compose-профиле и не раскрывает лишние management endpoints.
5. Добавить container smoke test: запустить инфраструктуру и приложение, дождаться статуса health, выполнить запрос к health endpoint и убедиться в корректном завершении контейнера при остановке.
6. Актуализировать инструкции запуска в README после выбора окончательной схемы портов.

**Критерии приемки:**

- Порты в `application.yml`, Dockerfile, Compose и README совпадают или различие явно обосновано конфигурацией окружения.
- `docker compose up` переводит контейнер приложения в статус `healthy`.
- Health check использует существующий endpoint и правильный management-порт.
- Smoke test воспроизводимо проходит в чистом локальном окружении.

## TD-2. Обеспечить согласованность MongoDB и Kafka через transactional outbox

**Приоритет:** высокий при критичности интеграционных событий.

**Проблема:** запись парфюма в MongoDB и публикация Kafka-события выполняются раздельно. Сбой между операциями создаёт состояние, при котором данные изменены без события либо событие опубликовано без подтверждённой записи.

**Задачи:**

1. Утвердить требования к доставке: какие события обязательны, допустима ли eventual consistency, срок доставки и политика восстановления после сбоя.
2. Спроектировать MongoDB-модель outbox-записи: стабильный идентификатор события, тип, версия контракта, ключ агрегата, payload, дата создания, статус/число попыток и диагностическая информация об ошибке.
3. Изменить create, update и delete парфюма так, чтобы изменение агрегата и создание outbox-записи фиксировались в одной MongoDB-транзакции; предусмотреть требуемую конфигурацию replica set для транзакционных тестов и production.
4. Реализовать отдельный publisher, который выбирает неопубликованные записи, публикует их в Kafka и помечает отправленными только после broker acknowledgement.
5. Добавить безопасные повторные попытки, backoff, метрики возраста старейшего необработанного события и алерт для записей, превысивших лимит попыток.
6. Реализовать идемпотентную обработку входящих сообщений по `event_id`: хранить или проверять уже обработанные ID, чтобы повторная доставка не изменяла агрегат повторно.
7. Подготовить процедуру эксплуатации: просмотр/повторная отправка зависших outbox-записей и правила очистки успешно опубликованных записей.
8. Покрыть интеграционными тестами сбой Kafka после MongoDB commit, повторную доставку и восстановление публикации после перезапуска.

**Критерии приемки:**

- Успешное изменение парфюма создаёт outbox-запись в той же транзакции MongoDB.
- Временная недоступность Kafka не приводит к потере события; после восстановления оно публикуется.
- Повторная доставка одного `event_id` не создаёт повторных изменений.
- Метрики и логи позволяют обнаружить и диагностировать зависшие сообщения.

## TD-3. Исправить обработку входящих Kafka-событий и исключить feedback loop

**Приоритет:** критический.

**Проблема:** delete-event маппится по `event_id` вместо идентификатора парфюма из payload. Кроме того, create/update, принятые из внешнего топика, используют сценарии, публикующие новые события, что способно зациклить обмен.

**Задачи:**

1. Проверить Protobuf-схему входящего события и определить единственный источник идентификатора парфюма для каждого `event_type`, включая `DELETED`.
2. Исправить mapper delete-event: передавать в команду удаления ID агрегата из payload, а `event_id` использовать только как идентификатор сообщения для трассировки и идемпотентности.
3. Разделить локальные команды, которые должны публиковать доменное событие, и команды синхронизации из внешнего потока, которые сохраняют состояние без повторной публикации.
4. Зафиксировать правила происхождения события: какие топики потребляет приложение, в какие публикует, допускается ли обработка собственных сообщений и как она предотвращается.
5. Добавить защиту от обработки сообщений собственного происхождения, если топологии producer и consumer могут пересекаться: отдельные топики, заголовок/атрибут источника или фильтрация по утверждённому признаку.
6. Добавить метрики обработанных, пропущенных, ошибочных и повторно доставленных событий с разбиением по типу.
7. Написать интеграционные тесты на create, update и delete: правильный ID при удалении, отсутствие повторной публикации при входящем сообщении, повторную доставку и направление ошибочного события в retry/DLT.

**Критерии приемки:**

- Delete-event удаляет парфюм, указанный в payload, а не сущность с ID события.
- Обработка входящего create/update/delete не порождает бесконечной или лишней цепочки исходящих сообщений.
- Автоматизированные интеграционные тесты проверяют полный event flow, retry и DLT.
- Документация содержит однозначную топологию и правила происхождения событий.

## TD-4. Зафиксировать и версионировать внешние контракты

**Приоритет:** высокий.

**Проблема:** REST create и update возвращают одинаковый `200 OK`, спецификация OpenAPI отсутствует, а стратегия версионирования событий не определена. Клиенты не получают стабильного машиночитаемого договора об API и эволюции событий.

**Задачи:**

1. Согласовать семантику REST-операций, включая успешные коды create/update/delete, формат ошибок, обязательность и ограничения полей, а также правила передачи идентификаторов.
2. Добавить и поддерживать OpenAPI-спецификацию REST API; включить все endpoints, request/response DTO, ошибки валидации и примеры.
3. Привести контроллеры и error resolver к утверждённому контракту; дополнить Jakarta Validation constraints там, где проверки должны быть видны клиенту до вызова domain.
4. Зафиксировать версию Kafka-события в контракте и правила эволюции: добавление optional-полей, запрет повторного использования номеров Protobuf, совместимость producer/consumer и период поддержки версий.
5. Определить версионирование gRPC/Protobuf-схем, процедуру review изменения `.proto` и проверку совместимости до публикации в Schema Registry.
6. Добавить contract-тесты REST и Protobuf-совместимости, запускаемые в CI вместе с тестами приложения.
7. Актуализировать README и `ARCHITECTURE.md`: ссылки на спецификации, политика версий и порядок уведомления потребителей о breaking changes.

**Критерии приемки:**

- OpenAPI описывает фактические REST-контракты и проверяется автоматизированным тестом.
- HTTP-коды и ошибки соответствуют утверждённой спецификации.
- Каждое Kafka-сообщение имеет явную версию, а правила совместимости доступны разработчикам и потребителям.
- Изменение `.proto`, нарушающее обратную совместимость, выявляется до публикации.

## TD-5. Внедрить аутентификацию, авторизацию и защищённую конфигурацию окружений

**Приоритет:** критический перед production.

**Проблема:** Spring Security подключён, но правила доступа, субъекты, ownership карточек и transport security не реализованы. JMX в Dockerfile запускается без authentication и TLS. Публичный запуск может открыть данные и служебные интерфейсы.

**Задачи:**

1. Утвердить модель идентичности: источник пользователей, механизм аутентификации, формат credentials/tokens, lifecycle сессии и требования для сервисных вызовов.
2. Определить модель владения: связать карточки пользователей и парфюмов с субъектом, описать административные полномочия и запрет доступа к чужим ресурсам.
3. Реализовать `SecurityFilterChain` по принципу deny-by-default: разрешить только требуемые публичные endpoints, защитить API и management endpoints отдельными правилами ролей.
4. Добавить resource-level authorization во все операции чтения, изменения и удаления; не принимать owner ID из недоверенного HTTP payload.
5. Настроить безопасные production-параметры: TLS и аутентификацию для MongoDB, Kafka и gRPC, секреты через внешнее хранилище/переменные окружения, ограничения размера HTTP/gRPC payload и защищённые логи.
6. Отключить JMX в production либо настроить authentication, TLS, сетевое ограничение доступа и отдельные credentials; сохранить небезопасный вариант только в явно локальном профиле.
7. Добавить security-тесты: неаутентифицированные запросы, недостаточные права, доступ к чужим ресурсам, защита Actuator и отсутствие секретов/персональных данных в логах.
8. Описать матрицу доступов, переменные окружения и безопасный production deployment в документации.

**Критерии приемки:**

- Все API и management endpoints имеют явно определённый режим доступа.
- Пользователь не может прочитать, изменить или удалить чужую карточку.
- Production-профиль не запускает незащищённый JMX и не хранит credentials в репозитории.
- Security-тесты подтверждают запрет неавторизованного и неразрешённого доступа.

## TD-6. Расширить автоматизированное покрытие критических границ

**Приоритет:** высокий.

**Проблема:** существуют тесты MongoDB-репозиториев и gRPC converter, но отсутствует покрытие REST-контроллеров, ошибок, use cases, Kafka producer/consumer/retry/DLT, gRPC server/client и запуска контейнера. Регрессии на транспортных и интеграционных границах не обнаруживаются автоматически.

**Задачи:**

1. Составить матрицу тестов по слоям и критическим сценариям; связать каждый тест с рисками TD-1--TD-5 и определить владельца поддержки тестового окружения.
2. Добавить unit-тесты use cases: нормальные CRUD-сценарии, отсутствие сущности, доменные инварианты, ошибки repository/gateway/event publisher и правила публикации.
3. Добавить HTTP-тесты контроллеров и error resolver: успешные ответы, валидация, некорректные UUID/поля, отсутствующие ресурсы, согласованные коды и JSON ошибок.
4. Добавить интеграционные Kafka-тесты на producer, consumer, deserialization, retry topics, DLT, delete mapping, идемпотентность и отсутствие feedback loop.
5. Добавить gRPC-тесты входящего сервера и исходящего клиента: успешный ответ, `NOT_FOUND`, deadline, retry и преобразование ошибок.
6. Добавить smoke test контейнерного запуска из TD-1 и тесты с реальными Testcontainers MongoDB/Kafka/gRPC mock там, где поведение зависит от сетевой интеграции.
7. Обеспечить изоляцию тестов, управляемые таймауты и очистку ресурсов, чтобы тестовый набор был стабильным в CI.
8. Настроить отчётность покрытия и минимальный порог только после формирования стабильной исходной базы; не блокировать сборку формальными метриками без проверки качества сценариев.

**Критерии приемки:**

- Автоматически проверяются REST, use case, Kafka, gRPC и container startup сценарии из архитектурного документа.
- Ошибки и retry/DLT проверяются без ручного запуска инфраструктуры.
- Тесты воспроизводимо проходят локально и в CI без зависимости от внешних сервисов.
- Матрица тестов показывает, какой сценарий покрывает каждый существенный риск технического долга.

## TD-7. Развить LangChain-агент до безопасного и полезного пользовательского интерфейса

**Приоритет:** средний после TD-4, TD-5 и критичных интеграционных задач.

**Проблема:** минимальный agent-service поддерживает лишь create/get/update известной карточки и является учебной натурально-языковой оболочкой. Без поиска, идентичности, ownership и контролируемого доступа его нельзя использовать как production-интерфейс.

**Задачи:**

1. Добавить отдельный ограниченный REST use case поиска и фильтрации по type, season, gender, concentration, longevity, sillage, availability и rating; валидировать фильтры, ограничить выдачу и добавить индексы под подтверждённые query patterns.
2. После search API добавить read-only tool, который вызывает только этот endpoint, а не выгружает каталог и не фильтрует данные LLM.
3. Ввести сервисную идентичность агента, минимальные роли, resource-level authorization после TD-5 и аудит без персональных данных.
4. Зафиксировать controlled confirmation: ID подготовленной операции, срок действия, однократность и защита от повторной отправки для create, update и будущего delete.
5. Добавить метрики запросов/tool-вызовов/ошибок/latency/неподтверждённых мутаций и изолированные end-to-end тесты со stub `my-scents`.

**Критерии приемки:** поиск выполняется только через ограниченный публичный API; агент не действует без идентичности, авторизации, ownership и отдельного подтверждения; tool не получает доступ к MongoDB, Kafka, gRPC или Java-домену.

## TD-8. Устранить ошибочные ожидания от LangChain-агента и определить production-границы

**Приоритет:** высокий перед любым production-развёртыванием agent-service.

**Проблема:** LLM является интерфейсом к API, а не заменой доменных сценариев, политик безопасности, поиска, качества данных или наблюдаемости. Неконтролируемое расширение полномочий создаёт риск prompt injection, SSRF, tool abuse, утечек и обхода authorization.

**Задачи:**

1. Закрепить, что бизнес-правила и доменная валидация остаются в `my-scents`; LangChain только выбирает allowlisted tool и формирует параметры.
2. Запретить прямые tools для MongoDB, Kafka, Schema Registry, gRPC, Docker, shell, файловой системы и произвольного HTTP; регулярно проверять whitelist paths, methods и JSON-schema.
3. Не передавать LLM персональные данные, токены, cookie, секреты, URI с credentials и полные технические HTTP body; отделить недоверенный контент от system instructions.
4. Запретить утверждать успешное выполнение до результата API, а при неоднозначных параметрах требовать уточнения без фабрикации enum, рейтинга или данных.
5. До production утвердить rate/size/time/cost limits, retention prompts/traces и threat model для injection, SSRF, replay confirmation и authorization bypass.

**Критерии приемки:** агент использует только объявленные tools и endpoints, не допускает SSRF/command execution/infra access, не совершает мутацию при ошибке или неоднозначности и не раскрывает секреты или персональные данные.

3. Выполнить TD-6 параллельно с исправлениями, начиная с регрессионных тестов для TD-1 и TD-3.
4. Выполнить учебный `langchain-agent` только как внешний локальный REST-клиент; до внешнего или production-использования завершить TD-5, TD-4 и TD-8.
5. Запланировать TD-2 после утверждения требований к гарантии доставки и операционной модели Kafka/MongoDB.
