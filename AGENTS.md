# Инструкции для AI-агентов

## Назначение и контекст

Эти инструкции специализируют **OpenCode** для проекта «Ароматека». OpenCode читает корневой `AGENTS.md`, затем ближайший `AGENTS.md` модуля, конфигурацию агентов из `.opencode/agents/` и тематические правила из `.opencode/instructions/`.

Для Python-кода используй `.opencode/agents/python-developer.md`, `python-code-reviewer.md`, инструкции `python-style.md`, `python-api-contracts.md`, `python-security.md`, `python-testing.md` и skills `python-development`/`python-code-review`/`python-api-contracts`/`python-security`/`python-testing`. Для LangChain-агентов используй `langchain-developer.md`, `langchain-reviewer.md`, инструкции `langchain.md`, `langchain-api-contracts.md`, `langchain-security.md`, `langchain-testing.md` и skills `langchain-agents`/`langchain-review`/`langchain-api-contracts`/`langchain-security`/`langchain-testing`. Правила для скриптов находятся в `scripts/AGENTS.md`.

«Ароматека» -- модульный монолит на Java 25 и Spring Boot. Приложение ведёт персональные карточки пользователей и парфюмов, хранит их в MongoDB, предоставляет REST и gRPC-интерфейсы и обменивается событиями парфюмов через Kafka. Руководство по запуску находится в `README.md`; фактическая архитектура, интеграции и известные ограничения -- в `ARCHITECTURE.md`.

### Мини-глоссарий

- `User` -- агрегат пользователя с персональными данными; email и телефон нельзя логировать.
- `Fragrance` -- агрегат карточки парфюма с характеристиками и идентификатором UUID v4.
- `boundary` -- входные и выходные порты, а также команды use case.
- `domain` -- агрегаты, value objects, инварианты и оркестрация сценариев.
- `adapter` -- транспортные и интеграционные реализации портов: HTTP, gRPC, Kafka и MongoDB.
- `infra` -- конфигурация и технические компоненты Spring, MongoDB, Kafka, gRPC и логирования.
- `FragranceEvent` -- Kafka-сообщение о факте создания, изменения или удаления парфюма.
- `event_id` -- идентификатор сообщения для трассировки и идемпотентности; это не ID парфюма.
- `payload.id` -- идентификатор парфюма, к которому относится `FragranceEvent`.
- DLT -- dead-letter topic для Kafka-сообщений, не обработанных после retry.
- value object -- тип доменного значения, централизованно проверяющий инварианты.

## Приоритет инструкций

При конфликте правил применяй следующий порядок:

1. Явные требования пользователя для текущей задачи.
2. Локальный `AGENTS.md` ближайшего затронутого модуля.
3. Корневой `AGENTS.md`.
4. `ARCHITECTURE.md` для архитектурных, технологических и проектных решений.
5. Тематические файлы из `.opencode/instructions/`.
6. Существующие соглашения и паттерны кода в модуле.

Если пользовательское требование создаёт риск потери данных, нарушения безопасности,
несовместимого публичного изменения или некорректной миграции, сначала укажи риск
и предложи безопасный вариант реализации.

## Общие правила

- Перед завершением выполни релевантные тесты и сообщи точные команды и их результат.
- Не изменяй публичные API, схему БД, зависимости и конфигурацию CI без явного обоснования в результате работы.
- Не добавляй зависимости, если задачу можно решить средствами языка, платформы или уже подключённых библиотек.
- Не меняй сгенерированные файлы.
- Если требования противоречат друг другу или информации недостаточно, остановись и задай уточняющий вопрос.
- Обязательно задай уточняющий вопрос до изменения публичного REST/gRPC/Kafka-контракта, схемы данных, security-политики, production-конфигурации, стратегии миграции или когда требования допускают несколько несовместимых вариантов.
- Допущение допустимо только для локальной обратимо́й доработки без изменения контракта, если оно подтверждается существующим кодом. Явно укажи такое допущение в итоговом ответе.
- Перед изменениями изучать затрагиваемые код и конфигурацию.
- Сохранять изменения минимальными и соответствующими существующей архитектуре.
- Не добавлять секреты, локальные файлы IDE и результаты сборки в Git.
- Изменения добавлять в git, но не делать commit.

## Ветки для изменений

- Для задачи, требующей изменений существующего кода или документации либо добавления новой доработки, сначала обнови локальную `main` из удалённого репозитория.
- Создавай от актуальной `main` отдельную ветку с префиксом `feature/` и выполняй работу только в ней.
- Имя ветки после `feature/` должно быть лаконичным, отражать суть задачи и быть записано в `kebab-case`, например `feature/add-fragrance-search`.
- Не переключай, не перемещай и не удаляй ветки с незавершёнными или чужими изменениями. Если обновление `main` или создание ветки блокируется такими изменениями, запроси дальнейшие указания пользователя.

## Документирование

- Актуализировать `ARCHITECTURE.md` в соответствии с внесёнными в код и архитектуру изменениями.
- Актуализировать все `README.md` в соответствии с внесёнными в код и архитектуру изменениями.
- Для **каждого полученного задания** до завершения работы создать в `promts/` отдельный файл Markdown с текстом задания. Файл создаётся даже для документационной, конфигурационной или исследовательской задачи.
- Имя файла: нижний регистр, ASCII, слова через дефис и расширение `.md`, например `promts/add-fragrance-search.md`. Если имя занято, добавь порядковый суффикс: `add-fragrance-search-2.md`.
- Файл задания содержит заголовок `# Задание: <краткое название>` и полный текст полученного задания без изменения смысла. Не включай в него секреты, персональные данные и служебные рассуждения агента.
- После выполнения добавь в **конец** `REPORT.md` одну запись о задании. Журнал ведётся строго сверху вниз в хронологическом порядке: старые записи не перемещай, новые не вставляй в начало или между существующими записями.
- Каждая запись `REPORT.md` обязана содержать текущую дату, краткий результат и Markdown-ссылку на созданный файл задания. Запись без ссылки недопустима.
- Используй шаблон:
```markdown
## 2026-09-18 -- Краткое описание выполненной работы

**Задание:** [add-fragrance-search.md](promts/add-fragrance-search.md).

Кратко перечислены фактически выполненные изменения и существенные ограничения.
```
- Перед завершением проверь, что файл из `promts/` существует, ссылка в новой записи разрешается, а сама запись добавлена последней. Добавь prompt-файл и `REPORT.md` в Git вместе с файлами задачи, но не создавай commit.

## Формат работы и ответа

- Перед нетривиальным изменением кратко сообщи, какие код, тесты и конфигурацию будут изучены. Для задачи только на анализ не заявляй изменения или проверки, которые не выполнялись.
- Финальный ответ по задаче с изменениями обязан содержать разделы `Изменения`, `Решения и ограничения`, `Проверка`.
- В `Изменения` перечисли затронутые файлы и наблюдаемое поведение, а не внутренние действия без результата.
- В `Решения и ограничения` укажи архитектурную причину, совместимость контракта, допущения и сознательно не затронутые границы.
- В `Проверка` приведи точные фактически запущенные команды, их результат и невыполненные проверки с причиной.
- Добавляй `План` только для нетривиальной задачи, по явному запросу пользователя или при наличии нескольких самостоятельных этапов.
- Для code review сначала перечисляй findings в порядке критичности с файлом и строкой; затем укажи пробелы проверки и краткое резюме.

## Проверочный чек-лист

Для каждой задачи с изменениями агент обязан оставить проверяемые следы выполнения:

- До первого изменения проверить, что активна отдельная ветка `feature/<kebab-case-name>`, созданная от обновлённой локальной `main`.
- Сохранить полный текст задания в новом `promts/<kebab-case-name>.md`.
- Для backend-изменения запросить независимое ревью агента `code-reviewer`, устранить подтверждённые замечания либо явно сообщить о принятом риске.
- Для Python-изменения запросить независимое ревью агента `python-code-reviewer`, а для LangChain-изменения -- `langchain-reviewer`; устранить подтверждённые замечания либо явно сообщить о принятом риске.
- Запустить минимальную релевантную проверку, затем предусмотренные модулем тесты и сборку, если изменён production-код, Protobuf или build-конфигурация.
- Добавить последней запись в `REPORT.md`, проверить ссылку на prompt-файл и добавить в Git только файлы текущей задачи без commit.
- В итоговом ответе перечислить ветку, изменённые файлы, ревью и результаты команд.

## Локальные инструкции

- При работе в подкаталогах учитывай ближайший `AGENTS.md`.
- Локальные инструкции уточняют правила корня, но не отменяют критичные требования по безопасности, тестированию и совместимости без явного указания пользователя.
