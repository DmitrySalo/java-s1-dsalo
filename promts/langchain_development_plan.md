**Evaluating agent service integration**

LangChain-агент следует добавить как самостоятельный Python-сервис в корень репозитория, например `langchain-agent/`. Он не становится частью Java/Gradle-модуля `my-scents`, не обращается к MongoDB, Kafka, gRPC или внутренним классам Spring Boot.

Единственная интеграционная граница агента с предметным приложением: публичный REST API `my-scents` по настраиваемому базовому URL.

```text
CLI / HTTP-клиент
        |
        v
langchain-agent (Python, LangChain, FastAPI)
        |
        | разрешённые HTTP-вызовы
        v
my-scents REST API (/api/v1/fragrances)
        |
        v
Spring Boot domain -> MongoDB / Kafka / gRPC
```

Это соблюдает существующую Clean/Hexagonal архитектуру: LangChain является отдельным внешним клиентом REST-контракта, а не новым адаптером внутри доменного кода `my-scents`.

## Минимальный полезный scope

Для домашнего задания сервис поддерживает только карточки парфюмов и три разрешённые операции:

| Операция агента | REST-вызов в `my-scents` | Польза |
| --- | --- | --- |
| Создать карточку парфюма | `POST /api/v1/fragrances` | Создание сущности по описанию на естественном языке |
| Получить карточку по UUID | `GET /api/v1/fragrances?fragranceId=<uuid>` | Безопасное чтение конкретной карточки |
| Обновить карточку | `PUT /api/v1/fragrances` | Исправление рейтинга и характеристик по естественному запросу |

Не включать `DELETE` в учебную версию: это снижает риск необратимой операции и не требуется критерием о 2-4 операциях.

Для любых изменяющих операций агент обязан запросить явное подтверждение пользователя. Пример:

```text
Пользователь: Добавь Dior Sauvage, рейтинг 8.

Агент: Будет создана карточка парфюма:
- name: Dior Sauvage
- rating: 8
- ...
Подтвердите создание: да / нет.
```

Только после `да` выполняется HTTP-вызов. Для CLI это можно реализовать интерактивным вводом; для HTTP-интерфейса агента подтверждение передаётся явным флагом `confirmed: true` в повторном запросе. Агент не должен интерпретировать фразы вроде «точно» или «давай» как подтверждение без отдельного шага.

## Контракт agent-service

Сервису достаточно двух собственных endpoints:

| HTTP | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | Проверка доступности самого agent-service; не проверяет и не раскрывает состояние `my-scents`. |
| `POST` | `/v1/agent/commands` | Принимает `message` и опциональный `confirmed`, возвращает нормализованный результат агента. |

CLI остаётся обязательным для задания и вызывает ту же прикладную логику:

```powershell
python -m app.cli "Создай парфюм Example, рейтинг 8, древесный, для зимы"
```

Ответ агента и HTTP endpoint должны возвращать один контракт:

```text
Status: success | confirmation_required | error
Action: <создание | получение | обновление | справка>
Data: <JSON-результат my-scents или подготовленная операция>
Errors: <массив ошибок либо []>
```

`confirmation_required` добавляется как безопасное расширение предложенного в задании контракта. Он явно сообщает, что изменения ещё не были внесены. После реального REST-вызова допустимы только `success` и `error`.

## Правила безопасности и интеграции

- `MY_SCENTS_BASE_URL` задаётся только через `.env` или переменные окружения.
- В `.env.example` указать безопасный пример: `MY_SCENTS_BASE_URL=http://localhost:8087`.
- Агент не принимает URL, hostname, порт или HTTP-метод от пользователя и LLM.
- HTTP-клиент строит адреса только из константного набора путей `/api/v1/fragrances`.
- Агент не имеет tools для shell, файловой системы, MongoDB, Kafka, gRPC, произвольного HTTP и управления Docker.
- В логах разрешены только тип операции, HTTP-метод, путь без секретов, безопасный UUID ресурса и HTTP-статус.
- Нельзя логировать request body, LLM prompt целиком, токены, `User.email`, `User.phoneNumber` или конфигурационные URI с credentials.
- Реализация предназначена исключительно для локального учебного профиля, пока не завершён `TD-5` об аутентификации и resource-level authorization.
- В production агент не должен вызывать create/update API до появления сервисной идентичности, минимальных прав и проверок владельца ресурса.

## TD-7. Развить LangChain-агент до безопасного и полезного пользовательского интерфейса

**Приоритет:** средний после завершения TD-4, TD-5 и критичных интеграционных задач.

**Проблема:** минимальный LangChain-сервис поддерживает только ограниченные операции с известными UUID и создан как учебная натурально-языковая оболочка. Без API поиска, модели идентичности, ownership и управляемого доступа он не должен использоваться как production-интерфейс.

**Задачи:**

1. Добавить поддерживаемый REST API сценарий поиска и фильтрации парфюмов для запросов по характеристикам:
    - тип;
    - сезон;
    - гендер;
    - концентрация;
    - стойкость;
    - шлейф;
    - доступность;
    - рейтинг.
2. Спроектировать поиск как отдельный use case `my-scents`, с ограничением выдачи, валидацией filter-параметров и индексами MongoDB под подтверждённые query patterns.
3. После реализации search API добавить read-only LangChain tool, который вызывает только этот публичный endpoint, а не загружает полный каталог и не фильтрует данные средствами LLM.
4. Реализовать сценарий безопасной поддержки оператора:
    - техническая сервисная идентичность агента;
    - минимально необходимые роли;
    - scope разрешённых операций;
    - аудит вызовов без персональных данных и секретов.
5. После завершения TD-5 включить resource-level authorization при всех вызовах агента к `my-scents`; агент не должен выступать от имени неопределённого пользователя.
6. Добавить controlled confirmation для всех изменяющих действий:
    - создание;
    - обновление;
    - удаление, если оно будет добавлено.
7. Зафиксировать UX и API-контракт подтверждения: идентификатор подготовленной операции, срок действия, однократность подтверждения и защита от повторной отправки.
8. Исследовать и согласовать сценарий инициирования существующего получения недостающей карточки через gRPC gateway из естественного запроса, не предоставляя агенту прямой gRPC-доступ.
9. Добавить трассировку и метрики agent-service:
    - количество запросов;
    - количество tool-вызовов;
    - распределение по операциям;
    - ошибки валидации;
    - ошибки upstream `my-scents`;
    - latency;
    - отклонённые и неподтверждённые мутации.
10. Добавить end-to-end тесты agent-service с изолированным stub `my-scents`, включая корректный выбор tool, точный HTTP-метод, подтверждение, ошибки API и запрет неразрешённых действий.

**Критерии приемки:**

- Агент выполняет естественно-языковый поиск только через публичный, ограниченный и тестируемый REST API.
- Агент не может получить или изменить ресурс без корректной идентичности, авторизации и проверки владельца.
- Любая мутация имеет отдельное подтверждение и аудит.
- Агент не получает прямого доступа к MongoDB, Kafka, gRPC и Java-домену.
- Метрики и безопасные логи позволяют диагностировать отказ agent-service и upstream API.
- Сквозные тесты подтверждают отсутствие вызовов неразрешённых endpoints.

## TD-8. Устранить ошибочные ожидания от LangChain-агента и определить production-границы

**Приоритет:** высокий перед любым production-развёртыванием agent-service.

**Проблема:** LLM-агент является интерфейсом к API, а не заменой доменных сценариев, политик безопасности, поиска, качества данных или наблюдаемости. Неправильное расширение полномочий может привести к несанкционированным запросам, галлюцинациям, утечке данных и обходу бизнес-правил.

**Задачи:**

1. Зафиксировать, что агент не заменяет REST, gRPC и Kafka-контракты:
    - бизнес-правила остаются в `my-scents`;
    - доменная валидация выполняется Java-приложением;
    - LangChain только выбирает разрешённый tool и формирует параметры.
2. Запретить агенту прямые инструменты для:
    - MongoDB;
    - Kafka;
    - Schema Registry;
    - gRPC;
    - Docker;
    - shell;
    - файловой системы;
    - произвольных исходящих HTTP-вызовов.
3. Реализовать и регулярно тестировать allowlist API paths, HTTP methods и JSON-схемы tool parameters.
4. Не предоставлять LLM пользовательские персональные данные:
    - `User.email`;
    - `User.phoneNumber`;
    - токены;
    - cookie;
    - секреты;
    - URI с credentials;
    - полные тела технических HTTP-запросов.
5. Разделить пользовательский текст и недоверенный внешний контент от системных инструкций; исключить возможность переопределения tool policy prompt-инъекцией.
6. Запретить агенту утверждать, что операция выполнена, до успешного результата реального API-вызова.
7. Определить поведение при неоднозначных параметрах парфюма:
    - агент запрашивает уточнение;
    - не выбирает произвольное enum-значение;
    - не фабрикует характеристики, рейтинг или результаты поиска.
8. Не использовать LLM как источник фактических данных о парфюмах. Внешние данные должны приходить через существующий доверенный сценарий `my-scents` и проходить доменную валидацию.
9. До production определить модель лимитов:
    - rate limit;
    - максимальный размер запроса;
    - ограничения времени LLM и HTTP-вызова;
    - budget/cost limits при переходе на облачного провайдера;
    - политика хранения prompts, ответов и traces.
10. Провести threat modeling agent-service, включая prompt injection, SSRF, tool abuse, утечки логов, replay подтверждений и обход authorization.

**Критерии приемки:**

- Агент использует только заранее объявленные tools и публичные endpoints.
- Агент не может быть использован для SSRF, выполнения команд, доступа к инфраструктуре или произвольных REST-вызовов.
- Ошибочный или неоднозначный запрос не вызывает мутацию и не создаёт ложное успешное подтверждение.
- Секреты и персональные данные отсутствуют в prompts, traces и логах.
- Threat model, security-тесты и операционные лимиты утверждены до production-развёртывания.
